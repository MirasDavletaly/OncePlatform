# Шорт-лист, дубли и результаты участия

Реализовано 22 октября 2026 года. Поля доступны в формах создания и изменения задачи, карточке, таблице, мобильном списке, канбане, REST, CSV и MCP. Права на изменение сохраняются: основные поля меняют администратор и координатор, закрытие — администратор.

## Поля и фильтры

| Поле API/MCP | Значение | Фильтр списка |
| --- | --- | --- |
| `fit_score` | Целое 1–5: от низкого к высокому соответствию | `fit_min`, `fit_max` |
| `complexity` | Целое 1–5: от низкой к высокой сложности | `complexity_min`, `complexity_max` |
| `market` | Текст до 120 символов | `market`: подстрока без учёта регистра |
| `applications_count` | Целое 0–2147483647 | `applications_min`, `applications_max` |
| `budget_amount` | Неотрицательная десятичная **строка**, до 16 цифр перед точкой и 2 после | `budget_min`, `budget_max` |
| `currency` | Трёхбуквенный код, по умолчанию KZT | `currency` |
| `customer` | Текст до 300 символов | `customer`: подстрока без учёта регистра |

Числа необязательны: `null` означает отсутствие данных. Ноль заявок и нулевая сумма — известные значения, а не пропуски. В числовых фильтрах пропуски не участвуют; при сортировке они идут в конце в обоих направлениях. Для суммы применяется существующая колонка PostgreSQL `numeric(18,2)`, JSON не переводит деньги во floating point.

По всем показателям можно сортировать через заголовки таблицы или `sort=<поле>&order=asc|desc`. Для сравнения сумм обязательна валюта: разные валюты не складываются в одну шкалу. Нажатие заголовка «Сумма» при отсутствии валюты выбирает KZT и открывает фильтры, где валюту можно изменить.

Пример для REST и CSV:

```text
/api/v1/tickets?fit_min=4&applications_max=3&deadline_from=2026-10-19&deadline_to=2026-10-25&sort=fit_score&order=desc
/api/v1/tickets/export.csv?fit_min=4&applications_max=3&deadline_from=2026-10-19&deadline_to=2026-10-25
```

Даты включают оба календарных дня в часовом поясе портала. Кнопка «Эта неделя» выбирает понедельник–воскресенье в том же поясе. В MCP `list_tickets` принимает те же поля фильтра в JSON. Список, экспорт и API канбана используют общий фильтр сервиса.

В REST PATCH отсутствие поля сохраняет значение, `null` очищает числовое поле, `""` очищает рынок/заказчика. В MCP `update_ticket` числовые поля очищаются через `clear_fields`, например:

```json
{"ticket_id":"T-2026-0001","clear_fields":["fit_score","budget_amount"],"applications_count":0}
```

Одновременно задать значение и включить то же поле в `clear_fields` нельзя. Изменения записываются в аудит. Существующие описания не разбираются автоматически: свободный текст не даёт надёжной классификации без проверки.

## Защита по ссылке

Форма заранее проверяет ссылку через `GET /api/v1/tickets/source-check?source_url=...` и показывает ссылку на существующую задачу. При редактировании передаёт `exclude_id`. Окончательная защита работает в PostgreSQL при создании и изменении, в том числе из MCP и при конкурентных запросах.

Ключ нормализует регистр схемы/хоста, стандартные порты и отсутствие `/` в корне; адрес без схемы трактуется как HTTPS. Сохраняются HTTP/HTTPS, регистр пути, query и fragment: они могут определять разные задачи. Параметры отслеживания и конечные `/` у непустого пути намеренно не удаляются.

Повтор возвращает HTTP **409**, код `duplicate_source_url`, сообщение с номером и `error.details.ticket` с `id`, `number`, `title`. MCP возвращает tool error с тем же кодом и номером. Пустые ссылки разрешены; закрытая задача продолжает резервировать ссылку. Мягкое удаление администратором освобождает её, если больше нет активных исторических дублей.

Для синхронизации:

1. Найти задачу через `list_tickets` с `source_url`.
2. Если найдена — прочитать и обновить подтверждённые поля через `update_ticket`.
3. Если нет — вызвать `create_ticket`. При `duplicate_source_url` повторно найти существующую задачу; другой процесс мог успеть создать её между проверкой и записью.

Конфликт не перезаписывает чужую карточку автоматически. Расписание внешних синхронизаций эта доработка не меняет.

## Просрочка и проигрыши

Просроченными считаются только `new`, `analysis`, `solution` с прошедшим дедлайном. `sent` и `closed` исключены из фильтра просрочки, ленты сроков, напоминаний и цветовых предупреждений. В карточках отправленных задач показывается обычная дата. При возврате из `sent` в подготовку просрочка снова рассчитывается.

При закрытии с `result=lost` обязательно `loss_reason`:

| Код | Причина |
| --- | --- |
| `price` | Цена |
| `competitor` | Конкурент |
| `no_response` | Нет ответа |
| `requirements` | Требования |

В MCP это параметр инструмента `change_ticket_status`:

```json
{"ticket_id":"T-2026-0001","status":"closed","result":"lost","loss_reason":"price","comment":"Заказчик подтвердил: предложение победителя дешевле на 18%."}
```

Инструкции MCP требуют брать причину из явных фактов или ответа пользователя и уточнять неизвестное. `no_response` означает действительно отсутствующий ответ, а не отсутствие сведений о причине. Встроенного LLM-процесса нет: выбор передаёт подключённый ИИ через MCP; сервис валидирует код и права. Форма закрытия в портале поддерживает тот же контракт.

Причина видна в карточке, истории и CSV, доступна через `list_tickets(loss_reason=...)`. `get_overview` и REST dashboard возвращают `lost_by_reason`, на главной показана разбивка с переходами к задачам. Старые проигрыши без причины попадают в `unknown`. Переоткрытие очищает текущую причину и результат, сохраняя предыдущий исход в истории; статистика учитывает текущее состояние задач.

## Миграции и проверки

Миграции `00002_shortlist.sql` и `00003_loss_reason.sql` применяются обычным механизмом запуска сервера. Старые дубли не удаляются и не мешают обновлению: таблица резервирования хранит число активных ссылок, а первичный ключ и триггер не дают добавить новый дубль. Перед эксплуатационным обновлением используется обычная резервная копия БД. Down-миграции удаляют новые поля и их данные; это не способ откатить приложение без потери новых данных.

Проверки:

```powershell
$env:TEST_DATABASE_URL='postgres://postgres@127.0.0.1:55432/postgres?sslmode=disable'
go test ./... -count=1
go vet ./...
cd web
npm test
npm run build
```

Интеграционный тест создаёт и удаляет отдельную схему в одноразовой тестовой БД. Проверяет upgrade с историческими дублями, rollback/reapply миграций, сохранение и очистку полей, точность денег, фильтры, аудит, одновременные вставки, конфликт изменения ссылки, освобождение ссылки, просрочку и причины проигрыша. Без `TEST_DATABASE_URL` этот тест пропускается.

`scripts/test_shortlist_http.py` проверяет работающий **одноразовый локальный** портал через сессию и авторизованный MCP: поля, экспорт, ошибки, дубли, причины и статистику. Требуются `TEST_PORTAL_URL`, `TEST_PORTAL_USER`, `TEST_PORTAL_PASSWORD` тестового администратора. Скрипт создаёт синтетические задачи, затем мягко удаляет их и отзывает свой временный токен.

Эти проверки выполнены на PostgreSQL 18; тесты Go, TypeScript, frontend unit tests, HTTP/MCP и production-сборка прошли. Проверка интерфейса кликами в браузере не выполнена: в среде нет подключённого браузера. Рабочая БД и опубликованный сервер не изменялись.
